# CTech Poker CLI — MVP design

**Date:** 2026-09-05
**Status:** approved for planning
**Scope:** new `cli/` Go module — a terminal client for CTech Poker (sandbox / play-money only in the MVP)

---

## 1. Goal

A single self-contained binary that lets a user authenticate and play a CTech Poker
table from the terminal, covering the same core loop as the web UI minus the visual
richness (animated reactions, felt, avatars). Distributed as cross-platform GitHub
releases so it installs anywhere.

Non-goals for the MVP: spectating without a seat, multiple simultaneous tables,
navigable hand history, run-it-twice / rabbit-hunt / paid winner-cards, real-money
play, OS keyring integration.

---

## 2. Prerequisites (blockers — must land before the CLI can seat a player)

The poker API deliberately restricts every interactive (non-GET) operation to the
first-party `poker` SPA client. `api/internal/api/v1/readscopes.go`:

- `enforceReadOnlyScope` returns `Forbidden` for any non-GET request unless
  `isFirstPartyPokerSession(claims)` is true — i.e. `claims.AZP == "poker"` and
  `claims.SID != ""`.
- The public `poker:*` delegated / API-key scopes are read-only by design; there is
  no grantable scope for joining a table or sending a game action.

A token issued to a new `poker-cli` OAuth client therefore cannot call
`POST /rooms/:id/join`, `POST /rooms/join-or-create`, `POST /rooms/:id/ready`, the
buy-in paths, or the `POST /players/me` profile bootstrap. Without the changes below
the CLI is limited to GET-only commands (`/profile`, `/achievements`).

**P1 — ctech-poker (code, this repo).** Turn the single first-party client id into a
set:

```go
// readscopes.go
var firstPartyPokerClientIDs = map[string]struct{}{"poker": {}, "poker-cli": {}}

func isFirstPartyPokerSession(claims *jwtverify.Claims) bool {
    if claims == nil || claims.SID == "" {
        return false
    }
    _, ok := firstPartyPokerClientIDs[claims.AZP]
    return ok
}
```

`firstPartyPokerClientID` (the `const`) is currently used only by
`isFirstPartyPokerSession`; replace it with the map. No other call site changes.
Covered by a new case in `readscopes_test.go`.

**P2 — ctech-account (config / data, not code).** Register an OAuth client:

- `client_id`: `poker-cli`
- type: `public` (no client secret; PKCE required)
- `redirect_uris`: `http://127.0.0.1/callback` plus the loopback forms the CLI needs
  — ctech-account already special-cases `localhost` / `127.*` / `::1` hosts
  (`handler/helpers.go`), and `authorize.go` validates the redirect against the
  registered list. Register `http://127.0.0.1/callback` and
  `http://localhost/callback`; the CLI appends the ephemeral port at runtime — **confirm
  during P2 whether ctech-account matches the redirect_uri ignoring port for loopback
  (RFC 8252 §7.3); if it requires an exact match, register a fixed port (e.g.
  `http://127.0.0.1:8765/callback`) and the CLI binds that port.**
- `allowed_scopes`: `poker:rooms:read poker:players:read poker:sessions:read
  poker:hands:read poker:achievements:read poker:stats:read
  poker:achievements:read` (read set — interactive ops are gated by first-party, not
  by scope).

This mirrors the still-open real-money blocker (`api/CLAUDE.md`): nothing in this repo
can grant it, and it must be covered in every environment's deploy reconciliation.

**Device authorization grant** (`urn:ietf:params:oauth:grant-type:device_code`) is
**not** required — ctech-account does not support it and the RFC 8252 loopback flow
covers a CLI fully. A separate ctech-account feature request may add it later; the CLI
would then gain a `--device` login path with no server-side change here.

## 3. Module layout

New Go module at repo root, separate from `api/`:

```
cli/
  go.mod                       module gopkg.aoctech.app/poker/cli
  cmd/poker/main.go            cobra root + command wiring
  internal/
    config/                    ~/.config/ctech-poker/{config.toml,credentials.json}
    auth/                      PKCE loopback flow, api-key exchange, token refresh
    rest/                      typed client for the poker REST API (rooms, players, achievements)
    wsclient/                  table WebSocket: auth frame, protobuf codec, reconnect
    proto/                     generated from ../proto/poker.proto (see §6)
    tui/                       bubbletea models: lobby prompts + table view
    game/                      snapshot -> view-model, hand-strength + narration helpers
  .goreleaser.yaml
  install.sh
```

Rationale for a separate module (not `api/cmd/pokercli`): the CLI has its own release
cadence and its own dependency set (bubbletea, lipgloss, cobra, a WS client) that
should never enter the server's build. Same repo so the `.proto` stays a single
source of truth and cross-cutting changes are one PR.

## 4. Releases

- Tags: `cli/vX.Y.Z` (Go submodule tag convention).
- `goreleaser` builds `linux`/`darwin`/`windows` × `amd64`/`arm64`, publishes a
  GitHub Release with archives + checksums, updates a Homebrew tap formula.
- `install.sh`: detects OS/arch, downloads the matching archive from the latest
  `cli/*` release, drops the binary in `~/.local/bin` (or `$PREFIX`).
- CI: a workflow triggered only on `push` of tags matching `cli/*` runs
  `goreleaser release`. The existing API workflows add `paths-ignore: ['cli/**']`
  (or an equivalent guard) so a CLI-only change never runs the API pipeline, and the
  API is never released.
- Version stamped via `-ldflags -X main.version=...` from the tag.

## 5. Authentication

### 5.1 Storage

`~/.config/ctech-poker/` (respecting `$XDG_CONFIG_HOME`):

- `config.toml` — `api_base_url`, `account_base_url`, `client_id` (default
  `poker-cli`), UI prefs (color mode, card suffix).
- `credentials.json`, `0600` — `{access_token, refresh_token, expires_at,
  token_type, obtained_via}`. `obtained_via` is `pkce` or `api_key`.

Directory created `0700` on first write. A corrupt or unreadable credentials file is
treated as "logged out", never a hard error.

### 5.2 `poker login` (PKCE loopback — RFC 8252)

1. Generate `code_verifier` (43–128 chars, unreserved) and
   `code_challenge = BASE64URL(SHA256(verifier))`.
2. Bind a `net.Listener` on `127.0.0.1:0` (or the fixed port from P2), path
   `/callback`.
3. Open the system browser (`xdg-open` / `open` / `rundll32`; print the URL as a
   fallback for headless) to
   `GET {account}/v1.0/authorize?response_type=code&client_id=poker-cli&redirect_uri=<loopback>&code_challenge=<challenge>&code_challenge_method=S256&scope=<read set>&state=<random>`.
4. The local handler validates `state`, extracts `code`, shows a "you can close this
   tab" page, and signals the main goroutine.
5. `POST {account}/v1.0/token` — `grant_type=authorization_code`, `code`,
   `code_verifier`, `redirect_uri`, `client_id`. Store the token set.
6. Timeout (120s) → clear error, no partial state written.

### 5.3 API key

`poker login --api-key <key>` (or `CTECH_POKER_API_KEY` env). The CLI calls
`POST {account}/v1.0/token` with `grant_type=api_key` (confirmed supported —
`ctech-account/api/internal/handler/token.go`) and stores the resulting short-lived
access token with `obtained_via=api_key`. No refresh token is issued for this grant;
when the access token expires the CLI silently re-exchanges the stored API key. The
raw key is kept in `credentials.json` (same `0600`) for that purpose.

Precedence when multiple are present: explicit `--api-key` flag > `CTECH_POKER_API_KEY`
env > stored credentials.

### 5.4 Refresh

Before any request, if `expires_at` is within a 60s skew window: `pkce` tokens
refresh via `grant_type=refresh_token` (rotating the stored refresh token —
ctech-account rotates on use); `api_key` tokens re-exchange as above. A `401` on any
call triggers exactly one refresh-and-retry, then surfaces "session expired, run
`poker login`".

## 6. Protocol / proto sharing

`scripts/generate-proto.sh` gains a third `protoc` invocation:

```sh
protoc -I "$ROOT/proto" \
  --go_out="$ROOT/cli/internal/proto" \
  --go_opt=paths=source_relative \
  --go_opt=Mpoker.proto=gopkg.aoctech.app/poker/cli/internal/proto \
  poker.proto
```

Generated `cli/internal/proto/poker.pb.go` is committed (same as the api copy). The
CLI does not import the `api` module. `lobby.proto` is not needed — the CLI's lobby
interactions are plain REST; only the table socket speaks protobuf.

Wire format on the table socket is **binary protobuf** (matching the server and web
UI — `api/CLAUDE.md`: "Transport is binary protobuf on both gateways ... 32 KiB frame
cap"). `ClientMessage` / `ServerMessage` envelopes as defined in `proto/poker.proto`.

## 7. REST client (`internal/rest`)

Thin typed wrapper over `net/http`. Injects `Authorization: Bearer`, handles the
`sendPage` envelope (`{data, has_next, next_cursor, ...}`), decodes RFC 9457 problem
responses into a Go error carrying `title` / `detail` / `status`.

Endpoints used by the MVP:

| Command | Calls |
|---|---|
| `/profile` | `GET /v1.0/players/me` (+ `POST /v1.0/players/me` bootstrap on 404 — needs P1) |
| `/achievements` | `GET /v1.0/players/me/achievements` |
| `/play` | `GET /v1.0/rooms/stakes?currency_mode=sandbox`, then `POST /v1.0/rooms/join-or-create` |
| `/enter {id}` | `GET /v1.0/rooms/:id`, then `POST /v1.0/rooms/:id/join` |
| in-table `/summary` | `GET /v1.0/players/me/sessions` (current session) |
| in-table `/share` | share code already on the room object from join; format + copy |
| leave | `POST /v1.0/rooms/:id/leave` (fallback if the WS `request_exit` path is unavailable) |

`join-or-create` / `join` bodies carry `currency_mode`, `small_blind`, `big_blind`,
`max_seats`, `amount` (buy-in, 20–100 BB, multiple of BB), `auto_rebuy`,
`idempotency_key` (a client-generated UUID, reused across retries of the same
command). `max_seats` is `2` (heads-up), `6` (6-max) or `9` (full-ring).

`buyin.ErrTermsNotAccepted` surfaces as a specific problem — the CLI prints the terms
URL and instructs the user to accept in the web app (the MVP does not implement a
terms-acceptance command).

## 8. Table WebSocket (`internal/wsclient`)

- Connect: `GET {api}/v1.0/tables/:tableId/ws` (scheme `wss`), `coder/websocket`.
- First frame after upgrade: `ClientMessage{type:"auth", token:<jwt>, share_code:<code if private>}`.
- Read loop decodes `ServerMessage`; a typed channel of decoded messages feeds the
  TUI. Write path is a serialized queue (one writer goroutine).
- Ping: reply to server pings; also send `ClientMessage{type:"ping"}` on the
  protocol's cadence.
- Reconnect: on unexpected close, exponential backoff (1s→30s, jitter), re-auth,
  send `ClientMessage{type:"sync_state"}`. The TUI shows a "reconnecting" banner and
  keeps the last snapshot visible (dimmed).
- `Origin` header: send a configured allowed origin (the API enforces an origin
  allow-list on the WS upgrade — `api/CLAUDE.md` issue #44; `cmd/loadtest` sets an
  `-origin` flag for the same reason). The CLI sends
  `Origin: https://poker.ctech...` (configurable), matching a listed first-party
  origin.

### 8.1 Client → server messages used

`auth`, `ping`, `sync_state`, `ready` (`ready:true/false` — backs `/ready` and
`/sitout`), `act` (`action` ∈ `fold|check|call|raise`, `amount`, `action_id`,
`expected_snapshot_version`, `expected_hand_id`), `peek_cards` (`card_index` optional),
`chat` (`message`, ≤ 50 chars), `reaction` (`reaction_id`, `target_player_id`),
`post_big_blind`, `show_cards`, `keep_seat`, `request_exit` / `cancel_exit`.

Ignored in the MVP (server still accepts them from other clients):
`set_run_it_twice`, `request_rabbit_hunt`, `request_winner_cards` /
`accept_winner_cards` / `decline_winner_cards`, `bot_challenge` (Turnstile — a CLI
cannot solve it; if the server issues a challenge the CLI surfaces "anti-bot check
required, continue in the web app" and disconnects. Acceptable for the MVP; revisit
if it triggers in practice).

### 8.2 Server → client messages handled

`connected` (store `conn_id`), `pong`, `state` (the `TableSnapshot` — drives the whole
view), `chat`, `error` (correlate by `action_id`; `code` ∈ `unavailable` →
auto-resync-and-retry, `invalid_action` → show and stop), `removed` (reason + settled
stack → leave the table view), `achievement_unlocked` (toast line in the log).
Others (`room_*`, `*_purchase_update`, `social_*`, `system_broadcast`) are logged at
most as a one-line notice.

### 8.3 `act` optimistic-concurrency contract

Every `act` carries `expected_snapshot_version` (from the latest `state`) and
`expected_hand_id`. A rejected `act` with `code:"invalid_action"` +
`ErrVersionConflict` semantics means the snapshot moved; the CLI resyncs and asks the
user to re-issue. A generated `action_id` (UUID) is reused on the auto-retry after an
`unavailable` error so the server's idempotency guard collapses duplicates.

## 9. TUI (`internal/tui`)

`bubbletea` + `lipgloss` + `bubbles/textinput`. Alt-screen, full-redraw on each
`state`. Layout **B** (approved):

```
─── Mesa "<name>" ── No-Limit Hold'em ── Blinds R$1 / R$2 ── 4/6 jogadores ───
  Pote R$ 24   Board A♥ 7♣ K♦   Sua mão A♠ Q♥ · par de ases · ~62%
  Posições  [D] Caio · [SB] Duda · [BB] Edu · [UTG] VOCÊ     ● SUA VEZ  turno 11s · time bank 30s
────────────────────────────────────────────────────────────────────────────
  <scrolling narration log>
  → Sua vez. Pote R$ 24. Pagar R$ 8.  ações: call 8 · raise 16–246 · fold
────────────────────────────────────────────────────────────────────────────
› _
```

### 9.1 Header (rebuilt from every snapshot)

- Table name, game type (`No-Limit Hold'em` — the only variant), blinds.
- Currency: `R$ <amount>` only in real-money rooms. Sandbox rooms render the bare
  number (no prefix, no "fichas" label).
- `<seated>/<max_seats> jogadores` from `seats`.
- Pot = sum of `pots[].amount`. Board from `board` (+ `board_two` / `board_split_at`
  ignored — RIT is out of scope; render `board` only).
- Own hand from the viewer's `Seat` hole cards; strength label ported from
  `ui/src/lib/pokerRules.ts` (`game.HandStrength`); equity from
  `ServerMessage.equity` (viewer-scoped) — shown only once the viewer has locally
  peeked (mirrors the web gate; see `api/CLAUDE.md` "Hidden information" — the
  server sends the viewer's own category/equity unconditionally and the client
  withholds it until peek).
- Positions: derived from `dealer_player_id` / `small_blind_player_id` /
  `big_blind_player_id` + `seats` order. Tags `[D] [SB] [BB]`, then `[UTG]`,
  `[MP]`, `[CO]`, `[HJ]`, … by distance from the button for the rest, `VOCÊ`
  highlighted.
- Turn state: `● SUA VEZ` / `Caio pensando`, `turno <n>s` from
  `action_deadline_unix_ms` vs `action_base_deadline_unix_ms` (the gap is time
  bank), rendered as a live countdown (a 1s `tea.Tick`).

### 9.2 Narration log

Append-only, scrollback via PgUp/PgDn. Each `state` is diffed against the previous to
emit human lines: blinds posted, street dealt (`— FLOP — A♥ 7♣ K♦`), each player
action (`Caio aposta R$ 8`, `Duda desiste`, `Edu paga`), showdown
(`HandOutcome` → `board`, revealed hands, `pot_results` → winners + payouts),
`achievement_unlocked`, chat (`Ana: nice hand`), reactions
(`Caio 👍 → VOCÊ`). The diff logic lives in `internal/game` and is unit-tested against
recorded snapshot sequences (the repo already has `jogo_exemplo.har` /
`bug_mao_infinita.har` to derive fixtures from).

When it's the viewer's turn, a `→` prompt line summarizes legal actions from
`legal_actions` (`actions`, `call_amount`, `min_raise_to`, `max_raise_to`, the
`*_pot_raise_to` shortcuts).

### 9.3 Commands + hotkeys

Input line parses `/`-prefixed commands. Bare hotkeys (`f` `c` `r` `p` `k`) map to
the common actions when the input is empty and it's the viewer's turn.

| Command | Effect |
|---|---|
| `/check` | `act check` (only if `check` ∈ legal actions) |
| `/call` | `act call` (amount = `call_amount`) |
| `/raise {to}` | `act raise` amount=`to` (validated against `min_raise_to`/`max_raise_to`) |
| `/pot` | `act raise` amount=`pot_raise_to` |
| `/allin` | `act raise` amount=`max_raise_to` |
| `/fold` | `act fold` |
| `/talk {msg}` | `chat` (≤ 50 chars, rejected client-side otherwise) |
| `/react {code} [player]` | `reaction` (catalog key; `player` required for thrown reactions) |
| `/peek [all\|1\|2]` | `peek_cards` (default both) |
| `/sitout` | `ready` `ready:false` — server applies at end of hand |
| `/ready` | `ready` `ready:true` |
| `/summary` | session recap (buy-in, current stack, net, hands, biggest pot) from `GET /players/me/sessions` |
| `/last-winners` | winners of the last N hands, from the narration log's own history |
| `/share` | format the invite URL from the room's share code, copy to clipboard (`atotto/clipboard`), print it |
| `/exit` | `request_exit`; on confirmation leave the table view. `/exit!` forces `POST /rooms/:id/leave` |
| `/help` | list commands |

`/react` catalog: fetch `GET /v1.0/wallet/reaction-purchase/catalog` (the
`sendPage` envelope; each entry carries an `owned` flag) once on table entry;
`/react` with no arg lists the owned codes.

### 9.4 Card rendering (`internal/game`)

`rank + suit-glyph`, colored:

| Suit | Glyph | Color |
|---|---|---|
| hearts | ♥ | red |
| diamonds | ♦ | blue |
| clubs | ♣ | green |
| spades | ♠ | bright white / bold |

`--cards=ascii` (or `NO_COLOR`) falls back to `Ah Kd 7c Qs` with no color. Single
Unicode playing-card glyphs (🂡…) are **not** used — poor terminal/font coverage.

### 9.5 Lobby flow (`/play`)

`bubbles` list prompts, not the table model:

1. Table size: `Heads-up (2)` / `6-Max (6)` / `Full Ring (9)`.
2. Stake: from `GET /rooms/stakes?currency_mode=sandbox` (a list of
   `{small_blind, big_blind, ...}`).
3. Buy-in: prompt within `20×BB … 100×BB`, default `100×BB`, must be a multiple of
   BB.
4. `POST /rooms/join-or-create` → `{room_id, created}`.
5. Hand off `room_id` to the table model: connect WS, auth, `ready:true`, render.

`/enter {id}`: `GET /rooms/:id` (private rooms need the share code passed as
`--code` or prompted) → same buy-in prompt → `POST /rooms/:id/join` → table model.

### 9.6 Loading / feedback

Every network step shows a `bubbles/spinner` with a label ("entrando na mesa…",
"conectando…", "sincronizando…"). No silent waits.

## 10. Root command surface

```
poker login [--api-key <key>] [--device]     # --device errors "not supported yet"
poker logout
poker play                                    # interactive lobby -> table
poker enter <room-id> [--code <share-code>]
poker profile
poker achievements
poker --version
```

Global flags: `--config <path>`, `--api-url`, `--account-url`, `--cards ascii|color`,
`--no-color`, `--verbose` (logs WS frames to a file).

`play` / `enter` are the only commands that enter the full-screen TUI; `profile` /
`achievements` print and exit.

## 11. Error handling

- Network / 5xx: retry with backoff for idempotent GETs; for mutations, surface the
  problem `detail` and let the user re-run (idempotency key makes a manual retry
  safe).
- `401` → one refresh-and-retry → else "run `poker login`".
- `403` on a mutation with the CLI's own client id → almost certainly the P1/P2
  blocker is not deployed in this environment; the message says so explicitly.
- WS drop mid-hand → reconnect + `sync_state`; the server is authoritative and the
  turn timer / time bank keep running server-side, so the reconnect banner also
  shows the (server-driven) countdown so the user knows how long they have.
- `removed` frame → leave the table cleanly, print the settled stack, return to
  shell.

## 12. Testing

- `internal/game`: snapshot-diff → narration, hand-strength labels, position tags,
  card formatting — table tests against fixtures derived from the `.har` captures.
- `internal/auth`: PKCE challenge/verifier correctness, the loopback handler
  (`httptest` account server), api-key exchange, refresh-on-expiry, one-retry-on-401.
- `internal/wsclient`: auth-frame ordering, protobuf round-trip, reconnect +
  resync, `act` optimistic-version plumbing, `unavailable` auto-retry with a stable
  `action_id` — against a fake WS server.
- `internal/rest`: `sendPage` envelope, problem-response decoding, bearer injection.
- TUI: `teatest` golden-frame tests for the table view given a fixed snapshot and
  for the lobby prompt sequence.
- No server-side test changes beyond `readscopes_test.go` (P1).
